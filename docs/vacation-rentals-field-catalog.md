# Vacation Rentals — Field Catalog (Data Dictionary)

> **Status:** Draft / discovery
> **Audience:** Voxtera team (engineering + product)
> **Last updated:** 2026-05-21
> **Companion to:** `voxtera-vacation-rentals-architecture.md`

---

## Purpose

The architecture doc establishes a three-layer information model (PMC → Cluster → Unit)
and describes Layer 3 as "~30–50 structured database fields per unit." That description
is correct in spirit but too flat to build from. Once you enumerate the facts a guest
actually asks the bot about, three things become clear:

1. **There is a layer missing** — the **building**. Apartment "4B" sits in a building
   whose street entrance, lobby code, parking garage, and garbage day are shared by every
   unit inside it, while the apartment door and WiFi are not.
2. **"Per-unit data" is not one kind of thing.** A door code changes every booking; a
   WiFi password changes a few times a year; a bed configuration never changes. They
   cannot share a storage or refresh strategy.
3. **Some facts must never be spoken to an unverified caller** — a door code or WiFi
   password is only disclosed to a guest matched to an active booking for that unit.

This catalog enumerates every fact the bot needs and tags each one along four dimensions,
so the catalog can be read directly as the schema for the PMC / cluster / building / unit
/ booking tables — and so onboarding knows which fields come from an API and which a human
has to type in.

---

## The scope model — five layers

The architecture doc's three layers expand to five. **Building** and **Booking** are
additions; see [Proposed amendments](#proposed-amendments-to-the-architecture-doc).

```
Layer 1: PMC          (the brand)            — one record per customer
    ↓
Layer 2: Cluster      (the neighborhood)     — the RAG layer, ~9 per example PMC
    ↓
Layer 3: Building     (the shared structure) — optional; one record per multi-unit building
    ↓
Layer 4: Unit         (the property)         — one record per rentable unit
    ↓
Layer 5: Booking      (the stay)             — one record per reservation
```

A unit either belongs to a **building** (an apartment/condo with shared entry) or is a
**standalone house** with no building layer. Layer 5 (Booking) is where all per-stay,
fast-changing data lives — including the door code, which the architecture doc currently
misfiles under Layer 3.

## Classification dimensions

Every field in the catalog is tagged on four axes.

**Scope** — which layer owns the fact: `PMC` · `Cluster` · `Building` · `Unit` · `Booking`.

**Volatility** — how the value changes over time:

- `Static` — set once, essentially never changes (bed config, unit quirks).
- `Semi-static` — changes occasionally, owner-driven (WiFi password, lobby code).
- `Policy` — a default that cascades down the layers and can be overridden (check-in time,
  pet policy). See [Resolution rules](#resolution-rules).
- `Per-booking` — a new value for every reservation (door code, guest name, dates).

**Sensitivity** — whether and when the bot may say it out loud:

- `Public` — may be stated to any caller.
- `Gated` — stated only to a caller verified against an **active booking for that unit**.
- `Gated+window` — gated, *and* only within a disclosure time window (e.g. door codes
  released from check-in day, suppressed after check-out).
- `Internal` — never voiced to the guest; drives routing/ops only (lock integration type,
  maintenance dispatch route).

**Source of truth → Storage** — where the fact originates and how Voxtera holds it:

- Sources: `PMS` (Guesty/Hostaway/webhook) · `Lock/Seam` (access platform) ·
  `Onboarding` (typed in at setup) · `Guidebook` (imported from an existing digital
  guidebook) · `Computed` (generated by Voxtera) · `Curated` (cluster knowledge).
- Storage: `Config` (key-value, loaded per call) · `RAG` (vector index) · `DB`
  (structured relational field) · `Live fetch` (**not stored** — queried at call time).

## Layer 1 — PMC (brand)

One record per customer. Stored as **Config**, loaded per call from the dialed number's
PMC mapping.

| Field | Volatility | Sensitivity | Source → Storage |
|---|---|---|---|
| Brand / company name | Static | Public | Onboarding → Config |
| Brand voice & persona | Static | Internal | Onboarding → Config |
| Customer-service hours | Semi-static | Public | Onboarding → Config |
| After-hours emergency line | Semi-static | Public | Onboarding → Config |
| Human-escalation route (phone / Telegram / Slack) | Semi-static | Internal | Onboarding → Config |
| Refund / cancellation policy (default) | Policy | Public | Onboarding / PMS → Config |
| Damage / security-deposit policy (default) | Policy | Public | Onboarding → Config |
| Pet policy (default) | Policy | Public | Onboarding → Config |
| Default check-in / check-out time | Policy | Public | Onboarding → Config |
| Default house rules (quiet hours, max guests, smoking) | Policy | Public | Onboarding → Config |
| Door-code disclosure window (e.g. from 12:00 check-in day) | Policy | Internal | Onboarding → Config |

## Layer 2 — Cluster (neighborhood)

One record per neighborhood (~9 for the example 550-unit PMC). This is the **RAG layer** —
the only layer that uses vector retrieval.

| Field | Volatility | Sensitivity | Source → Storage |
|---|---|---|---|
| Restaurants, cafés, bars, brunch spots | Semi-static | Public | Curated / Onboarding → RAG |
| Transit, taxis, airport routes | Semi-static | Public | Curated → RAG |
| Pharmacies, hospitals, clinics, grocery | Semi-static | Public | Curated → RAG |
| Attractions & things to do | Semi-static | Public | Curated → RAG |
| Local events, festivals, seasonal notes | Semi-static | Public | Curated / feed → RAG |
| Cultural notes & etiquette | Static | Public | Curated → RAG |
| Local emergency numbers (police, ambulance) | Static | Public | Curated → RAG / Config |

---

## Layer 3 — Building (shared structure) — NEW LAYER

One record per multi-unit building; units link to it via `building_id`. Standalone houses
have no building record. Stored as **DB**.

| Field | Volatility | Sensitivity | Source → Storage |
|---|---|---|---|
| Street address | Static | Gated | PMS / Onboarding → DB |
| Front-door / lobby entrance instructions | Static | Public | Guidebook → DB |
| Lobby / building access code or fob | Semi-static | Gated+window | Onboarding → DB *(or Lock/Seam → Live fetch if per-stay)* |
| Parking — garage entrance & visitor rules | Semi-static | Gated | Onboarding → DB |
| Garbage / recycling schedule | Static | Public | Onboarding → DB |
| Elevator / floor / stairs notes | Static | Public | Onboarding → DB |
| Shared amenities (gym, rooftop, laundry) | Static | Public | Onboarding → DB |
| On-site contact (concierge / building manager) | Semi-static | Public | Onboarding → DB |

The **entrance protocol** is two-staged: a building-scoped step (get into the building)
followed by a unit-scoped step (get into the apartment). Modeling them at one layer was
the original mistake.

## Layer 4 — Unit (property)

One record per rentable unit. Stored as **DB** — lookup, not retrieval; no vector
embedding.

| Field | Volatility | Sensitivity | Source → Storage |
|---|---|---|---|
| Unit ID / internal name | Static | Internal | PMS → DB |
| Unit display name / listing title | Static | Public | PMS → DB |
| Lock type & integration handle (Seam device ID) | Static | Internal | Onboarding / Seam → DB |
| WiFi network name (SSID) | Semi-static | Gated | Onboarding → DB |
| WiFi password | Semi-static | Gated | Onboarding → DB |
| Apartment / unit-door entry instructions | Static | Public | Guidebook → DB |
| Bed configuration & sleeps-N | Static | Public | PMS → DB |
| Appliance instructions (oven, washer, AC/thermostat) | Static | Public | Onboarding → DB |
| Unit quirks ("press the dishwasher door hard") | Static | Public | Onboarding → DB |
| Trash disposal within the unit | Static | Public | Onboarding → DB |
| Assigned parking spot number | Static | Gated | PMS / Onboarding → DB |
| House-rules override (quiet hours, max guests, smoking) | Policy | Public | PMS / Onboarding → DB |
| Pet-policy override | Policy | Public | PMS / Onboarding → DB |
| Check-in / check-out time override | Policy | Public | PMS / Onboarding → DB |
| Emergency equipment locations (extinguisher, first-aid, shutoffs) | Static | Public | Onboarding → DB |
| Maintenance contact / dispatch route for this unit | Semi-static | Internal | PMS / Onboarding → DB |

**WiFi credentials are the field with no upstream owner.** Unlike the door code, most PMCs
have no API and no system of record for the WiFi password — it lives in a PMS custom
field, a guidebook, or a sticker on the router. So Voxtera legitimately *stores* it: an
onboarding-collected, semi-static DB field. (Exception: a PMC running StayFi-style per-stay
WiFi — see [Open questions](#open-questions).)

## Layer 5 — Booking (the stay) — NEW EXPLICIT LAYER

One record per reservation. Mostly **DB**, synced from the PMS. The access codes are the
exception: **Live fetch**, never stored.

| Field | Volatility | Sensitivity | Source → Storage |
|---|---|---|---|
| Booking reference (PMS-native) | Per-booking | Internal | PMS → DB |
| Voxtera numeric short code (for DTMF) | Per-booking | Internal | Computed → DB |
| Normalized reference (for voice lookup) | Per-booking | Internal | Computed → DB |
| Guest name | Per-booking | Gated | PMS → DB |
| Guest phone (caller-ID match) | Per-booking | Internal | PMS → DB |
| Guest preferred language | Per-booking | Internal | PMS / detected → DB |
| Party size | Per-booking | Gated | PMS → DB |
| Check-in date & time (this stay) | Per-booking | Gated | PMS → DB |
| Check-out date & time (this stay) | Per-booking | Gated | PMS → DB |
| Early check-in / late check-out granted | Per-booking | Gated | PMS → DB |
| Payment / balance-due status | Per-booking | Gated | PMS → DB |
| Special requests / booking notes | Per-booking | Internal | PMS → DB |
| Booking status (confirmed / cancelled / active) | Per-booking | Internal | PMS → DB |
| **Unit door code / smart-lock PIN** | **Per-booking** | **Gated+window** | **Lock/Seam (or PMS) → Live fetch — never stored** |
| Per-stay building access code (if the building issues one) | Per-booking | Gated+window | Lock/Seam → Live fetch |

## Resolution rules

### Cascade — for `Policy` fields

Policy fields resolve **most-specific-wins**, walking up the layers until a value is found:

```
Booking override → Unit override → Building override → PMC default
```

A value is stored only at the layer where it differs from the inherited default. The PMC
record carries `check_in_time = 16:00` once; only the handful of units that differ carry
their own value; a single booking that bought early check-in carries a booking-level
override. This is the structured-data equivalent of the architecture doc's "don't
duplicate" argument for RAG — it is why "16:00" is not copied across 550 unit rows.

### Gating — for `Gated` and `Gated+window` fields

Before the bot voices any **Gated** field, it must have matched the caller to an **active
booking for the specific unit under discussion** (via caller-ID or booking-reference — see
the architecture doc, Problem 3). Identity alone is not enough; it must be identity *for
that unit*.

**Gated+window** fields add a time test: the current time must fall inside the disclosure
window. Door codes are released from the PMC's configured check-in hour and suppressed
after check-out — the bot does not read a door code to a guest three days early.

**Internal** fields are never spoken; they only drive routing (which lock to query, which
maintenance team to ticket). **Public** fields have no restriction.

### Live fetch — for the door code and per-stay building code

These are fetched from the access platform (via Seam) or the PMS **at call time** and held
only in memory for the duration of the call. Rationale: the code is regenerated every
booking and can be rotated mid-stay; a stored copy goes stale and the bot reads a dead code
to a guest standing at the door. The unit row stores the *lock integration handle*; the
*code itself* is never persisted.

## Proposed amendments to the architecture doc

1. **Layer model 3 → 5.** Insert **Building** between Cluster and Unit; add **Booking** as
   an explicit layer. The current doc's "structured data per unit" silently merges
   unit-static facts with per-booking dynamic facts.
2. **Line 95 fix.** "Address, building access code, smart-lock code, wifi password" is
   listed as Layer 3 (Unit) data. Re-file: *building access code* → Building layer;
   *smart-lock code* → Booking layer, **Live fetch, never stored**; *address* → Building
   layer; *WiFi password* stays at Unit.
3. **Line 90 unchanged.** "~9 RAG indexes" is still correct — Building and Unit are
   structured DB, not RAG. Only the Cluster layer uses vector retrieval.
4. **Add a source-of-truth note to Problem 1.** Door codes always have an authoritative
   upstream owner (PMS or access platform) → live fetch. WiFi credentials usually have
   none → onboarding-collected DB field. They look alike but are mirror opposites.
5. **Extend Problem 5 (multi-tenancy).** The new `buildings` and `bookings` tables also
   need a `pmc_id` column, indexed and filtered on every query.

## Schema implication

Five tables, each carrying `pmc_id`:

- `pmcs` — Layer 1, served as Config.
- `location_clusters` — Layer 2, each holding a handle to its RAG index (`pmc_id +
  cluster_id`).
- `buildings` — Layer 3, new.
- `units` — Layer 4, with a **nullable** `building_id` (null = standalone house) and
  nullable override columns for each Policy field.
- `bookings` — Layer 5, new as an explicit entity.

The door code is **not a column on any table**. It is a call-time fetch through the
Seam / PMS adapter, cached only for the live call.

## Open questions

- **Per-stay WiFi.** If a PMC runs StayFi-style WiFi that rotates per booking, does the
  WiFi password become Booking-scoped + Live fetch, like the door code? The catalog
  currently models the common case (a static Unit field).
- **Building assignment.** How is a unit attached to a building at onboarding — explicit
  PMC input, or inferred from the street address? This decides whether Building is a clean
  layer or a fuzzy one.
- **Guidebook import.** Can existing Touch Stay / Duve / Hostfully guidebook content be
  ingested to pre-fill the `Guidebook`-sourced Unit and Building fields, or is every one of
  them manual onboarding?
- **Disclosure window.** Is the door-code release window a fixed rule (check-in day 12:00)
  or PMC-configurable? The catalog assumes the latter and models it as a PMC policy field.
